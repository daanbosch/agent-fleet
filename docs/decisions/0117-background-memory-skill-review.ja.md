## 背景

Issue #1559 は hermes がやっていることを求めている。直前のセッションの内容を読み、そこからメモリとスキルを
整えるレビューパスである。hermes は動作中のエージェント自身のターンをフォークする。Agent Fleet は CLI を
所有していないのでターンをフォークできない。できるのは、セッションのトランスクリプトに対して別の、ツールを持たない
単発のモデル呼び出しを走らせることで、これは既存のタイトル提案と同じ形である。

本書のために読んだ、ツリーに既にあるもの：

- **全 kind が一つの経路で書けるストア。** 0108 以降、af MCP の 5 つのツールは AF 自身のストアに書く
  （`memoryx/agent_memory.go` の `agentMemSave`）。リビジョン確認、シークレットスキャン、変更ごとに 1 コミット
  （0022 の履歴に `AF-Author-Kind` / `AF-Author-Session` トレーラー付き）、そして diff・revert・forget を備えた
  Console の変更一覧（`agent_memory_changes.go`）がある。ユーザー単位の `agentMemory` スイッチの背後にあり、
  既定はオフ。`memory_roots.go`（claude と codex のネイティブツリー）はもう書き込み経路ではない。スイッチが
  オンの間 claude のネイティブ書き込みはオフで（0108 決定 6 手順 2）、codex のネイティブメモリは既定でオフである。
- **安価な補助ターンの経路。** `chatx.OneShotHeadless(ctx, feature, tier, persona, prompt, model)` は
  バックエンドを選び（機能ごとの固定、なければ共有の優先順。現在は claude、codex、opencode、cursor、agy で、muse は固定
  した場合のみ）、ヘッドレスで実行し、内部から呼び出し側の `usagex.Tag{Feature, Trigger, Ref}` を付けた
  台帳の行を 1 行記録する（`usagex.RecordCall`）。**どのバックエンドでもツールなしの呼び出しになるわけではない。**
  claude は `--tools ""` と `--no-session-persistence` で動くが、codex の `--ephemeral` は永続化を省くだけ、
  opencode のワンショット設定（`OpencodeOneShotConfig`）は edit と bash を拒否するが read や Web アクセスは拒否
  せず、設定を書けなければ設定なしにフォールバックする。agy のワンショットは `read_url` を許可する。提案系
  機能は出力が短いラベルなのでこれを許容してきたが、第三者のテキストを読み、URL の取得を唆されうるレビューは
  許容できない。タイトル・ブランチ名・返信候補・翻訳が既にこの経路を使っている。
- **凍結された台帳の列挙。** 新しい消費者には `internal/usagex/ledger.go` の `Feature*` 定数、0029 §2 の最初の `| feature |` 行の値、Console の ja カタログのエントリーが要る（色と AI アシストの行も
  あるが強制はされない）。最初の二つがずれると `usage_features_catalog_test.go` が落ちる。
- **ターン終了のシグナル。** Agent のセッションごとのステータス記録（`internal/status`）は `TurnEnd`、
  `TurnEndAt`、`TurnEndReason` を持ち、claude と codex のフック、opencode のプラグイン、managed ドライバーが
  書く。フックのない 4 つの TUI kind はセッション一覧のポーリングで観測される。
- **既存トリガーの落とし穴が一つ。** 自動タイトル提案はトランスクリプトの*読み出し*ハンドラー
  （`sessionx/session_transcript.go`）から始まる。つまり Console がそのセッションを見ている間だけ動く。
  バックオフのコメントもそう書いている。このパターンを写したバックグラウンドレビューは、無人または
  スケジュール実行のセッションでは静かに一度も動かない。トリガーの先例として正しいのは、メモリスイッチの
  レベルトリガー型リコンサイラー（`memoryx/agent_memory_autosync.go`）である。永続化された状態と世界を
  起床のたびに比べる、Agent 内のループだ。
- **スキルには今、書き込み経路がない。** `fleetskills` はイメージの `notes/` のトピックを、claude
  （`$CLAUDE_CONFIG_DIR/skills`）、codex（`$CODEX_HOME/skills`）、opencode（`~/.config/opencode/skills`）、
  muse（`~/.config/muse/skills`）のユーザースキルルートへ、所有マーカー付きの `af-<topic>` ディレクトリとして
  コピーする。マーカーのあるディレクトリだけが削除される。agy はプロジェクト側の `.agents/skills` しか読まず、
  copilot・cursor・kiro・lcpp にはユーザースキルルートがない。

## 決定

1. **トリガー：ターン終了とウォーターマークによる、Agent 内のレベルトリガー型ループ。手動の「今すぐレビュー」を併設。**
   ループは定期的に、また Agent 起動時に起きて、次がすべて成り立つセッションを対象にする。レビュースイッチと
   AF メモリ（`agentMemory`）がオン、セッションにトランスクリプトがある（`Caps().CanTranscript`。shell と ssm は除く）、
   ステータスが本物のターン終了（AF が仮に idle とみなしただけでない。下記）を示してから落ち着き時間
   （提案 120 秒。レビューは高いのでタイトルの 45 秒より長い）以上経っている、セッションの永続ウォーターマーク
   以降に新しいターンが K 件以上ある（提案 K = 10。hermes の「10 ターンごと」にならう）、セッション自体がレビュー
   ではない。トランスクリプトのある kind はすべて対象で、スケジュール実行や子セッションも含む。無人の経験が
   溜まるのはそこだからである。
   - **ターン終了の証拠。** ステータス記録の `TurnEnd` では足りない。agy・copilot・cursor・kiro では、Console
     かドライバーがポーリングしない限り立たない（`sessionx/turn_end_poll.go` はセッション一覧のポーリングで
     終了を記録するだけで、`lastTurnEndAt` は別ストアの `ObservedTurnEnd` も採用する）ので、無人の TUI
     セッションはステータス記録上 `working` のままになる。そこでループ自身がこれらの kind のライブソースを
     ポーリングし、`TurnEnd`、または同じ記録リビジョンに紐づく `ObservedTurnEnd` のいずれかを証拠として採用する。
     観測を記録するために `PersistTurnEnd` を呼んではならない。完了通知が使うゲートを消費してしまう。
   - **実行は確保され、復旧できる。** 実行はセッション識別子と固定した窓の終端（確保時のトランスクリプト位置）
     をキーとし、補助モデルを呼ぶ*前に*永続的に記録する。これで手動と自動が同じ窓を確保できず、再起動後は窓を
     推論し直さず同じ実行を再開する。実行記録には補助呼び出しの状態、キューに入れた提案、適用済みの操作を
     持つ。キューに入れてから最初の公開までの間に停止した場合の復旧は、記録済みのものを適用またはスキップ
     するだけで、その窓についてモデルに再度問い合わせない。ウォーターマークは実行が終わったとき、操作ゼロ・保留
     のみ・no-op のみの実行も含めて窓の終端へ進める。形式不正の返答は失敗として実行を終え、決定 3 の試行予算を
     使い切った後にだけ進める。同じ実行内で同じ対象への操作が複数あれば、キューに入れる前に最後の一つにまとめる。
2. **入力は AF が組み立てる、伏せ字済みの窓。** 補助モデルが見るもの：未レビューのターン（文字数の予算、新しい方を
   残す、提案 40,000 文字）、プロジェクトの現在の `memory_index` の行、窓とのキーワード重なり（`memory_search` の
   ランキング）が高い既存メモリ最大 5 件の全文。これで「既存を直す、新規を作らない」「書く前に読む」を、期待では
   なく構造として担保する。伏せ字処理は、完全にデコードした各入力文字列（トランスクリプトの
   ターン、インデックス行、メモリ本文）に対し、窓を予算で切り出す*前*に行う。切り出しで鍵が二つに割れると、
   どのルールにも一致しなくなるからだ。0022 のスキャナー（`memoryScanContent`）は伏せ字処理器ではない。マスク済み
   ヒントと行番号を返し、同一行の同一ルールのヒットを一つにまとめ、20 件で打ち切る。上限があると、最初の 20 件を落とした後の 21 件目の
   秘密が通ってしまうので、入力は次の三つのうちちょうど一つの方法で作る。(a) 検出が 1 件でもあればその入力
   フィールド全体を捨てる、(b) 各行を独立にスキャンして検出のある行を捨てる、(c) 全スパンを列挙する処理器。
   上限に達したらそのフィールド全体を捨てる。NUL バイトを含む文字列や、スキャンが
   失敗した場合は送らない。返答も、メモリ本文だけでなく理由・根拠・キューのメタデータを含む全フィールドを保存前
   に同じスキャンにかける。ツールの出力や取得したページは、プロンプトの中でデータとして印を付ける。これは
   緩和策であって境界ではない。トランスクリプトには第三者が書いた内容（Web ページ、Issue）が入りうる。決定 6 の
   ゲートはそのために存在する。
3. **補助ターンは `OneShotHeadless` の 1 呼び出し。P0 で弱すぎると分かる場合を除きティアは `OneShotShort`。台帳の
   新機能は `memory.review`。** トリガーは `auto`（「今すぐレビュー」は `manual`）、`Ref` はレビュー対象セッション名。
   台帳でセッションごとのレビュー費用を示せ、使用量ビューでレビューを独立した列として出せる。バックエンドは機能の
   固定または共有の順序で、**レビュー対象セッションの kind とは限らない**。つまりトランスクリプトは、メンバーが
   既にアシスタント機能に使っているプロバイダーへ行く。**使えるのは、全ツール・MCP サーバー・ファイル・ネット
   ワークアクセスを拒否した状態で動かせるバックエンドだけ**である。レビューは専用の全拒否設定を持ち、その設定を
   書けない、または検証できないときはそのバックエンドを飛ばし、既定のまま動かすことは決してしない（フェイル
   クローズ）。その保証を出せないバックエンドではレビューを走らせない。opencode・codex・agy でこれを成り立たせる
   ことは P1 の必須部分で、それまでは claude だけが条件を満たす。この機能は他のワンショット機能と同様に設定 → AI アシスト
   に行を持ち、メンバーがエージェントとモデルを固定できる。台帳の列挙、Console のカタログ、色、0029 §2 の
   日付付き注記は 1 コミットで入れる。`usage_features_catalog_test.go` が強制するのはそのうち二つ、Console の ja
   カタログのエントリーと、値が 0029 §2 の最初の `| feature |` 行に現れることである。表の下の注記では後者を
   満たさない。したがって、過去の追補と同様に、その行へ値を足して理由を日付付き注記に書くか、テストを日付付きの
   追記も読むよう拡張する。それ以外で凍結された本文は編集しない。色と AI アシストの行はこのテストでは強制され
   ない。1 回あたりの上限は P3 ではなく P1 から必須である：窓ごとの有限の試行予算（呼び出し 1 回、再試行は高々
   1 回。その後は実行を失敗として保留し、新しいターンが来るまでその窓を再度対象にしない）、決定 2 のインデックス
   行と本文（各々 200 KiB になりうる）を含む入出力の合計上限、セッション横断で共有する同時実行の上限。数字だけが
   P0 とオーナーを待つ（提案：出力は 5 操作、各 8 KiB）。
4. **モデルは提案し、AF が適用する。** 返答は JSON の操作リスト：メモリの `create` / `update` / `forget`（後で
   決定 7 のスキル操作）で、各操作に対象名、新しい本文、一行の理由、根拠となるターン番号を持たせる。AF が
   パースして検証する（名前、0108 決定 3 の上限、AF が組み立てた入力から取ったベースリビジョン）。形式が崩れた
   返答は丸ごと捨てる。決定 3 のバックエンド契約（ツールなし、ファイルなし、ネットワークなし）の下では、混乱した、または
   注入された補助モデルが作れるのは、AF が検査するテキストだけである。書き込み先：
   - **メモリ、全 kind：AF ストア。** af MCP のツールと同じ `agentMemSave` / `agentMemForget` 経路を通し、
     *レビュー対象セッションの*プロジェクト（0108 決定 2）にスコープする。kind に依らない事実はユーザースコープ。
     全 kind が af MCP 経由でストアを読むので、レビュー対象の kind 専用の書き込み先は要らない。だから
     `memory_roots.go` の外にいる kind（opencode、agy、copilot、cursor、kiro、lcpp、muse）も claude や codex と
     同じコードで賄える。
   - **ネイティブメモリツリー（claude の `*/memory/**`、codex の `memories/**`）：書かない。** claude のネイティブ
     書き込みは AF スイッチの下で既にオフ。codex のそれはメンバー個別の選択（0112）。
   - **スキル：決定 7。**
5. **バージョン管理とロールバックは 0022/0108 の履歴を再利用し、新しい仕組みは作らない。** 適用された提案は
   通常の 1 コミット公開で、作者種別は `review`（既存の `agentMemKindRe` が既に通す値）、作者セッションは
   レビュー対象セッション、`AF-Review-Run: <id>` トレーラーを付ける。変更一覧に出て、変更ごとの revert と forget は
   従来どおり動き、「この実行を revert」はその id を持つコミットを新しいコミットとして revert する。履歴は
   書き換えない。既存の revert はそのメモリの最新の変更しか受け付けないので、実行内の各コミットは、revert の
   時点でそのメモリの最新の変更である場合だけ戻す。その後メンバーやエージェントが編集したものは手を付けず、
   競合として報告し、上書きしない。複数操作の実行は部分的にしか戻せないことがあり、再実行は戻せるものだけを
   再試行する。メンバーが却下した提案は内容ハッシュで覚え、同じ案を再提案しない。forget したメモリはレビューでは復活させ
   ない。`agentMemSave` はこれを自動では保証しない。存在しない名前へのリビジョン 0 の create は許され、墓標の
   リビジョンを引き継ぎ、墓標を消してしまう。したがってレビューの `create` は、墓標または過去の存在が見つかれば
   拒否し、その確認は保存と同じストアのロック内で行い、キューの提案の承認時や `auto` の適用時にも再度確認する
   （間に forget があったかもしれないため）。
6. **承認ゲート：提案は既定でキューに入る。直接公開は別の、後の、メンバーが選ぶモード。** ユーザー単位の設定
   `memoryReview` の三値：`off`（既定）、`propose`、`auto`。0108 決定 8 は、全セッションが `AGENT_TOKEN` とシェルを
   持つのでゲートは悪意あるエージェントを止められないとして承認キューに反対した。その論拠はここには移らない。
   このゲートは悪意あるセッションに対するものではなく、*第三者が書いたかもしれないテキストを根拠に、無人のモデル
   が自分の判断で書く*ことに対するものだからだ。補助モデルに何かを書けと頼んだ人はいないので、エージェントの
   `memory_save` と違って尊重すべき意図がない。`propose` では提案は、ストアの隣（メモリリポジトリの外。未承認の
   テキストが公開履歴に入らない）の保留キューのファイルになる。メンバーは設定 → エージェントメモリで、既存の
   変更一覧の隣から承認・却下・全却下をし、その diff を再利用する。Console の通知（`memory-sync` 通知のパターン）
   が保留件数を伝える。承認は保存したベースリビジョンで通常の公開を通して適用し、ベースが古ければ提案を stale
   にして上書きしない。`auto` ではメモリの提案を同じ検査を通して即公開し、事後に見つけて戻す。0108 決定 8 が
   エージェントの書き込みを扱うのとまったく同じである。**スキルは `auto` を使わない。** キューのコスト（承認の
   負担、読まれずに承認されるか、スイッチを切られるキュー）は 0108 が挙げたものと同じで、既定がオフであり、重く
   感じるメンバーのために `auto` があるので、ここでは受け入れる。
7. **スキル：AF 所有の別ストア。常に承認ゲート付き。ユーザースキルルートがある kind にだけ配布する。メモリ経路が動く
   前には作らない。** スキルは命令として読まれる（0108 決定 7 はメモリを「証拠であって命令ではない」とする）ので、
   悪いスキルは悪いメモリより害が大きく、より厳しく扱う。ユーザースコープのみ。プロジェクト固有の教訓はメモリへ
   行く。作業コピーの `.agents/skills` には書かない。メンバーのリポジトリに未コミットの変更を残すからだ。ストアは
   同じマウント配下に置き、履歴はメモリリポジトリ内に独自のパスクラスで持つ（`agentMemRepoPathRe` は
   `af/(user|projects/…)/<name>.md` しか通さないので、スキルには独自のパターンが要る。さもないと変更一覧が
   それを伏せてしまう）。同じルールでスキャンする。配布は `fleetskills` に倣い、claude・codex・opencode・muse
   のルートにスキル 1 つにつきディレクトリ 1 つを置く。ただし fleetskills の `af-` ノートとは**接頭辞もマーカーも
   別**にして、互いの同期が相手のディレクトリを消さないようにする。agy・copilot・cursor・kiro・lcpp は何も
   受け取らない。教訓がメモリとしても保存されていれば、そちらで届く。「新規より修正」は入力で担保する
   （決定 2）。キーワードが合う既存スキルをプロンプトに入れ、既存とほぼ同名・同説明の `create` は `update` の提案に
   変換する。
8. **オプトインと失敗モード。** 既定はオフ、ユーザー単位。スイッチの隣に、会話の抜粋が固定された、または既定の
   アシスタントプロバイダーへ送られること、トークンを消費することを平易に書く。失敗と、それを無害にする挙動：
   - 使えるバックエンドがない、または呼び出しが失敗：バックオフ。ウォーターマークは動かさず、何も公開しない。
     一時的な失敗では通知を出さない。
   - 形式が崩れた、または大きすぎる返答：丸ごと捨て、数えて、バックオフ。
   - 提案にシークレット：エージェントの書き込みと同様に既存のスキャンが拒否。補助モデルは再試行しない。
   - ベースリビジョンが古い、名前の衝突：提案を stale にし、マージしない。
   - 空回り（毎回同じ提案）：決定 5 の却下ハッシュの記憶と、決定 3 の試行予算と、`auto` モードでは P3 の 1 日あたり実行上限。
   - 同じプロジェクトの同時レビュー：ストアのロックとリビジョン確認で直列化し、負けた側の提案は stale になる。
   - 実行中にワークスペースが停止またはクラッシュ：次の起床で、決定 1 の実行記録の内容に従って再開する。未送信なら
     送信する。送信済みで応答不明なら、決定 3 の試行予算の範囲内でのみ再試行し、前の試行は「コスト不明」として
     数える。応答またはキューが保存済みなら補助モデルを再度呼ばず、記録済みのものを適用またはスキップする。
     ウォーターマークは決定 1 のとおりにのみ進む。台帳の行はモデルが応答した後に
     遅延呼び出しで書かれるので、課金後・応答前の停止やクラッシュでは行が残らず、異常終了ではトークン数が不明
     になりうる。そこで決定 1 の実行記録は送信前に永続的な試行エントリーを保存し、復旧時に使用量の行があれば
     それに紐づけ、なければ Console で「コスト不明」と示す。すべてのコストが台帳にあるとは約束しない。
   - レビューのレビュー：補助呼び出しはセッションではなくトランスクリプトを持たないので、レビュー対象にならない。
   - 補助モデルのテキストがトランスクリプトを保留キューに写す：キューのファイルはストアと同じ非公開マウントの、
     シークレットスキャン済みの成果物で、承認または却下で削除し、ハッシュだけが残る。
9. **フェーズ。** サイズは見積もり。
   - **P0、S（#2319）：測る。** 実ワークスペースで、アイドル窓ごとのトランスクリプトサイズ、補助ターン 1 回の
     コスト、手動で回したときの提案量を測り、提案上限を直す。
   - **P1、M（#2320）：公開なしのエンジン。** ターン終了を自前でポーリングするループ、実行の確保と復旧記録、伏せ字済み入力、
     フェイルクローズの全拒否バックエンド契約、台帳に `memory.review` を載せ送信前に永続的な試行記録を残す補助
     ターン、検証、保留キュー、必須の試行・入出力・同時実行の上限（数字は P0 待ち）、`memoryReview` 設定
     （`off` / `propose`）、「今すぐレビュー」。台帳の列挙、カタログ、0029 の行、AI アシストの行を含む。
   - **P2、M（#2321）：承認 UI と公開。** 設定 → エージェントメモリの保留一覧、承認・却下、通知、`review` 作者と
     実行 id、「この実行を revert」（競合の報告付き）、却下ハッシュの記憶、承認時の墓標の再確認。
   - **P3、S（#2322）：`auto` モードと予算。** オーナーが未決事項 1 と 2 に答えた後だけ。P1 が既に強制する上限に加えて、1 日あたり実行上限を足す。
   - **P4、L（#2323）：学習したスキル。** ストア、スキャン、常にゲート付きの承認、別の接頭辞とマーカーで 4 つの
     ルートへ配布。

## 却下した案

- **hermes 式の、動作中ターンのフォーク（「同じモデル、同じキャッシュ済みプロンプト」）。** AF は CLI を所有して
  おらず、4 つの kind にはフックの接点自体がない。
- **自動タイトルのように、トランスクリプトの読み出しでトリガーする。** Console が開いている間しか動かないので、
  無人のセッションは一度もレビューされない（背景）。
- **N 回のツール呼び出しごと、またはターンごと。** コストが学ぶべきことの量ではなく活動量に比例し、ターンの途中は
  要約に向かない。ターン終了と K ターンの窓なら、同じ意図でより低い頻度になる。
- **セッションの停止・削除時だけレビューする。** 停止されないセッションが多く、停止や再作成で窓が失われる。
- **古いトランスクリプトへの夜間スイープだけをトリガーにする。** フックのない kind には効くが、教訓が遅れ、
  停止中のワークスペースを起こす。後から二つ目のトリガーとして足してもよい（本書では計画しない）。
- **claude のネイティブメモリや codex の `memories/` に書く。** リビジョン確認・スキャン・作者記録を迂回する
  （0108 の却下案）。codex では独自の統合パイプラインと衝突する。
- **補助モデルに af MCP のツールを持たせ、自分で `memory_save` を呼ばせる。** 行動することで公開してしまい、
  モデルの誤りや注入されたテキストが全 kind の次のセッションへそのまま届く。構造化された提案の契約は、AF を唯一の
  書き手に保つ。
- **自動公開を既定にする。** 決定 6 を参照。明示的なモードとしては残す。
- **作業コピー内のプロジェクトスコープのスキル。** メンバーのリポジトリを汚す。
- **スキルを 0042 のユーザー指示に書く。** 0042 決定 8 を無効にする。

## 結果

- 誰もエージェントに保存を頼まなくても、経験をメモリにできる。履歴・スキャン・revert はメンバーが既に持つもの
  と同じで、コストはレビュー対象セッションごとに独立した台帳の列として見える。
- 新しい失敗の類型が生まれる。もっともらしいが間違った教訓を書く補助モデルである。既定はキューなので、他の
  どのセッションより先にメンバーが目にする。代償は受信箱である。
- 伏せ字済みのトランスクリプトが、メンバーがセッションごとには選んでいないプロバイダーへ行く。スイッチの文言で
  それを伝え、機能の固定で行き先を選べる。
- レビューはワークスペースの停止中には動かない。Agent 側の他の機能と同じ（0022）。
- `memory.review` は 0029 の列挙に、書き換えではなく日付付きの注記で追加される。

## オーナーへの未決事項

いずれもコスト・既定値・承認の体験に関する選択で、ここでは意図的に決めない。

1. **スイッチをオンにしたときのモード：`propose`（推奨）か `auto` か。** 本書はメモリでは `propose`、スキルでは
   常にゲート付きを既定とする。`auto` を既定として提示してよいかはオーナーが決める。
2. **コストの上限。** 開始点の提案は、セッションあたり新規 10 ターンにつき 1 レビュー、同時実行は 1、1 日あたりの
   実行上限。その数値と、無人・スケジュール実行のセッションにそもそも適用するかはオーナーが決める。P0 が
   実測値を出す。
3. **トランスクリプトを、レビュー対象セッションの kind 以外のプロバイダーへ送ってよいか。** 既定は共有の
   ワンショット順序に従う。レビューをセッション自身の kind に固定すれば、ある kind のトランスクリプトを別ベンダーへ
   送らずに済むが、ヘッドレスで動かせない kind が落ちる。
4. **承認はどこに置くか。** 設定 → エージェントメモリのみ（推奨。場所が一つで、新しい UI 部品が要らない）か、
   レビューが提案を作ったセッションのミラーにもバナーを出すか。
5. **スキルは最初のリリースの範囲か。** 推奨はメモリが先（P1〜P2）、スキルはその後（P4）で、メモリレビューが
   コストに見合うと分かった場合だけ。
6. **却下した提案のハッシュと保留テキストをどれだけ保持するか。** 提案：保留テキストは決定時に削除し、ハッシュは
   対象のメモリが forget されるまで保持する。
