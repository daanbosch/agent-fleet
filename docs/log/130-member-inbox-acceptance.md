# 130. メンバー間の受信箱（ADR 0111 P1-A）の受け入れ条件

- 依頼: #1960 の第 1 部（ADR 0111 決定 14 の P0）。設計判断: [decisions/0111](../decisions/0111-member-collaboration.ja.md)
  （決定番号は本文と 2026-10-10 の Addendum のもの）。
- 状態: **条件だけを書いた**（2026-10-11）。受信箱はまだ無い。実機での確認は P1-A（#1961）の PR が行う。
- 使い方: P1-A の PR は、ここに並べた ID（`A-1` … `V-7`）ごとに「合格／不合格／未実施」と証拠
  （HTTP の状態コードと本文、SQL の出力、画面の撮影）を表にして載せる。未実施で残すものは Issue にして、
  その番号を表に書く（CONVENTIONS §10）。**未実施を合格と書かない。**

各条件には「誰が何を操作するか」と「どこで何を見れば合格か」を書いた。受信箱の具体的なルート名・表名は
P1-A が決めるので、ここでは役割で呼ぶ（§130.1）。P1-A の PR は役割名と実名の対応を先頭に書く。

## 130.1 登場人物・道具・観測点

**人とテナント**

| 名前 | 何か | 必要な条件 |
|---|---|---|
| A | 送信者。テナント T1 のメンバー | — |
| B | 受け手。T1 のメンバー | — |
| C | 2 人目の受け手。T1 のメンバー | §130.3 の `R-1` だけが要る（3 つ目のアカウント） |
| T2 | 別のテナント | §130.2 の `A-3`・`A-4` と §130.5 が要る。作るにはデプロイ管理者の権限が要る |

2 つのアカウントでできないのは `R-1`（2 人の受け手が同時に引き受ける）だけである。3 つ目のアカウントが
用意できないときは `R-1` を実機では「未実施」とし、§130.3 の Go のテストを証拠にする。ほかの競合
（`R-2`〜`R-4`）は送信者と受け手の 2 人で起きるので、2 アカウントで実機確認できる。

**観測点**

| 役割名 | 何か | 見方 |
|---|---|---|
| 受信箱 API | membership だけで認可する REST（決定 8。`withMembership`） | 各自のブラウザの開発者ツールで `fetch()`。Cookie はそのブラウザのものが付く |
| 受信箱ストリーム | 受信箱専用の SSE（決定 8。`GET /api/events` ではない） | 開発者ツールの Network タブ、または `new EventSource()` |
| 項目の表 | 受信箱の項目（共有状態・担当者）を持つ CP の表 | SQL |
| 配達の表 | 受け手ごとの配達状態・連番・既読位置を持つ CP の表 | SQL |
| `workspace` | ワークスペースのレコード（`membership_id` が UNIQUE） | SQL。`SELECT id, state FROM workspace WHERE membership_id = $1` |
| `memo` | メモの列（取り込んだレシピの行先） | SQL、または Console のメモ欄 |
| `audit_log` | 監査記録 | `GET /api/admin/audit`（テナント管理者） |
| エージェントの見え方 | `list_memos` の結果 | 受け手のセッションで「`list_memos` を呼んで結果をそのまま見せて」と頼む |

membership の id は `GET /api/admin/tenants/{slug}/members` で引ける。

**同時に押す方法**（`R-*` で使う）。2 つのブラウザの開発者ツールで、同じ時刻に発火するよう予約する。

```js
const at = Date.parse("2026-10-20T10:00:00+09:00");   // 両方に同じ時刻を入れる
setTimeout(async () => {
  const r = await fetch("/api/<claim のルート>", { method: "POST" });
  console.log(r.status, await r.text());
}, at - Date.now());
```

時計のずれが数十 ms あるので、実機では「同時」は粗い。だから実機は 20 回繰り返し、細かい競合は Go の
テストで示す（§130.3）。

**データベースは 2 種類**。CP は SQLite と Postgres の両方で動く。P1-A の Go のテストは
`AF_TEST_DATABASE_URL` を付けて Postgres でも走らせ、両方の結果を PR に載せる（`docs/build/10-development.md`
§10.4）。実機の配備はどちらか一方なので、どちらで確かめたかを書く。

## 130.2 認証と宛先（決定 2・8・10・11、Addendum 5）

| ID | 操作 | 合格の条件 |
|---|---|---|
| A-1 | ログインしていない状態で、受信箱 API の一覧・送信・状態変更を叩く | どれも 401。項目の表に行が増えない |
| A-2 | A が、宛先に次の 3 つを入れて送る: 実在しない識別子／T2 だけのメンバー／T1 で削除済み（`status=inactive`）のメンバー | 3 つとも**同じ**状態コードと同じエラーコードで断られる（どれが「存在しない」か見分けられない）。項目の表にも配達の表にも行が増えない。宛先の一部だけが不正でも、項目そのものを作らない（正しい宛先にだけ届く形にしない） |
| A-3 | B を T1 と T2 の両方に入れる。A（T1）が B に送る。B は `X-AF-Tenant: T2` と `T1` で一覧を取る | T1 で取ったときだけ見える。T2 では件数 0、バッジも 0。ストリームも T2 を選んでいる接続には何も流れない |
| A-4 | T2 のメンバー（T1 に属さない）が、A-3 の項目の id を知っているものとして、詳細・既読・引き受け・辞退を直接叩く | すべて 404（403 ではない。存在を漏らさない）。項目の状態は変わらない |
| A-5 | T1 のメンバーでも宛先でない人（C がいれば C、いなければ T1 の管理者）が、項目の id で詳細と引き受けを叩く | A-4 と同じく 404。一覧にも出ない |
| A-6 | 受け手の受信制御（決定 10）: B が「選んだメンバーからだけ受け取る」にして A を外す／B が A をブロックする。その後 A が B に送る | どちらも B の配達の表に行が増えない。A に返る結果は §130.8 の未決 1 の決着どおり。宛先に B と別の人がいる項目では、別の人には届く |
| A-7 | 通知を止める設定（do-not-disturb。決定 10）を入れた B に A が送る | 配達の表には行が増える（配達は止まらない）。B のバッジとトーストだけが出ない。辞退扱いにならない |
| A-8 | 上限（Addendum 5）: 宛先 21 人の項目／同じ送信者からの 1 時間で 31 件目／同じ A→B で未処理 11 件目／本文サイズの上限を 1 バイト超える | それぞれ断られ、行が増えない。断り方（状態コード）は P1-A が決めて PR に書く。20 人・30 件目・10 件目・上限ちょうどは通る（境界の両側を見る） |
| A-9 | エージェントからは送れない（決定 11）: B のワークスペースの中から、Agent が持つ資格情報（メモトークン `AF_MEMO_TOKEN`、Agent トークン）で受信箱 API を叩く | 401 か 404。`/internal/` の下に受信箱の口が無い。セッションの MCP ツール一覧に受信箱の送信・名簿のツールが無い |
| A-10 | 送信の監査（決定 9）: A-2〜A-8 の後で `GET /api/admin/audit` を見る | 送れたものは「誰が・何の種類を・誰に・いつ」が残る。本文はどこにも無い |

## 130.3 引き受けの競合（決定 2 の状態表）

| ID | 操作 | 合格の条件 |
|---|---|---|
| R-1 | A が B と C の 2 人に依頼を送る。B と C が同じ時刻に引き受けを押す（§130.1 の方法）。20 回、毎回新しい依頼で | 毎回、成功するのは 1 人だけ。負けた側は 409 で、本文に現在の状態 `claimed` と担当者が載る。項目の表の担当者は 1 人、状態は `claimed`。負けた側の画面は「◯◯ が引き受けました」になり、引き受けボタンが消える |
| R-2 | A が B に依頼を送る。B の引き受けと A の取り下げを同じ時刻に押す。10 回 | 最終状態は毎回 `withdrawn`。B の引き受けが先に通った回は、B に「取り下げられた」が届く（決定 2）。B の引き受けが後だった回は B に 409。**B の画面が「引き受けた」のまま `withdrawn` の項目を持っている瞬間が残らない**（再読み込みせずに見て確かめる） |
| R-3 | B が引き受けた依頼で、B の完了と A の取り下げを同じ時刻に押す。B の手放しと A の取り下げでも同じ。各 10 回 | 完了×取り下げ: 最終状態は `done` か `withdrawn` のどちらか一方で、負けた操作は 409。手放し×取り下げ: 最終状態は `withdrawn`（手放しが先なら `open` を経由する）。どちらも A と B の画面が同じ最終状態に揃う |
| R-4 | B が 2 つのタブから同じ依頼を続けて引き受ける（ダブルクリック・再送） | 担当者は B のまま 1 人。2 回目は成功扱いか、担当者が B 自身だと分かる 409 か（どちらにするかは P1-A が決めて書く）。B の画面にエラーの赤が出ない |
| R-5 | 最終状態（`done` / `declined` / `withdrawn`）の項目に、引き受け・辞退・手放し・完了・取り下げをそれぞれ叩く | すべて 409。状態は変わらない |

**Go のテスト（実機の代わりにはならないが、`R-1` は 3 アカウントが無いとき唯一の証拠になる）**: 引き受けを
50 本の goroutine から同時に呼び、成功がちょうど 1 本であることを、SQLite と Postgres の両方で示す。
**数えてから更新する形は同時の 2 要求が両方通る**ので、状態が `open` であることを条件にした 1 本の
更新（決定 2）で実装していることもテストで押さえる。陽性対照として、条件を外した版で同じテストが
落ちることを PR に書く。

## 130.4 open / claimed の依頼があるときのメンバー削除（決定 2 の状態表、決定 9）

メンバーの削除は 2 段ある。**論理削除**（テナント管理者の「メンバーを外す」＝`DELETE /api/admin/memberships`、
`membership.status` が `inactive` になる）と、その後の**物理削除**（`DELETE /api/admin/tenants/{slug}/members/{key}`、
行そのものと紐づく行を消す）。条件は両方で確かめる。論理削除は再招待で元に戻るので、その場合も見る。

| ID | 操作 | 合格の条件 |
|---|---|---|
| M-1 | B が引き受けた依頼がある状態で、管理者が B を論理削除する | 項目は `open` に戻り、担当者が空になる。A の一覧で「誰かを待っている」に戻る。C がいれば C の待ち一覧に再び出る |
| M-2 | A が B と C に送った `open` の依頼で、C が辞退した後に、管理者が B を論理削除する | B は数えられない（決定 2）ので、残る受け手は全員辞退済み＝項目は `declined` になる。A の一覧でそう見える。C がいないときは §130.8 の未決 2 の決着どおり |
| M-3 | A が送った `open` の依頼と、B が引き受けた依頼がある状態で、管理者が A を論理削除する | どちらも `withdrawn`。引き受けていた B に「取り下げられた」が届く。B の待ち一覧から消える |
| M-4 | B が A をブロックする（B が担当者の依頼がある状態で） | その依頼は `open` に戻る（状態表の system 行）。B の待ち一覧から消え、辞退の数からも外れる |
| M-5 | 論理削除された B が、削除前に開いていた受信箱ストリームと、削除後の受信箱 API | ストリームは削除の時点で切れる（`withResolved` の接続登録と同じ働き。決定 8）。次の REST は 401 か 403 |
| M-6 | M-1 の後で B を再招待する | 状態の遷移は巻き戻らない（`open` に戻った依頼は `open` のまま。誰かが引き受けていればその人のまま）。B は、まだ `open` の依頼の待ち一覧に再び出る（宛先は送信時に固定、取れるかどうかは今の membership で決まる） |
| M-7 | 論理削除した A・B を物理削除する | エラーにならない（外部キーで止まらない）。消えた人の配達の行と既読位置が消える（決定 9）。参加者が全員消えた項目は本文ごと消える。参加者が残っている項目は残り、残った人からは読める。`audit_log` の送信記録は残る |
| M-8 | M-7 の直後に CP 側の消去処理（決定 9 の purge）を 2 回続けて走らせる | 2 回目は何も消さない（冪等）。孤児の本文が残らない（項目の表と配達の表を membership の表と突き合わせて 0 行） |

## 130.5 ワークスペースをまだ持たない受け手（決定 8）

**罠**: Console の画面を開くと、起動時に `GET /api/events` などの `withResolved` のルートが走り、その場で
ワークスペースのレコードが作られる。これは今の動きで、受信箱とは関係ない。だから「受信箱を使っても
レコードが作られない」は、**Console の画面を一度も開かずに**受信箱 API だけを使って測る。Console を
開いたうえで見られるのは「受信箱を使ってもワークスペースが**起動しない**」だけである（`W-3`）。

ワークスペースを持たないメンバーを作るには、T2 に B を新しく招待する（B がまだ T2 で一度もログイン
していないこと）。A も T2 に入れておく。

| ID | 操作 | 合格の条件 |
|---|---|---|
| W-1 | 招待した直後に `workspace` を引く | B（T2）の行が無い（出発点の確認。ここで行があれば以下は測れない） |
| W-2 | B が `/login?next=/api/<受信箱一覧のルート>?tenant=<T2>` からログインする（画面ではなく JSON に着地する）。A（T2）が B に DM と依頼を 1 件ずつ送る。B はその JSON のページの開発者ツールから、一覧・既読・ストリーム・引き受け・手放し・辞退・完了を順に叩く | 全部が成功する。その後も `workspace` に B（T2）の行が無い。コンテナ／タスク／EC2 が起動していない（管理画面のメンバー一覧で B のワークスペースが「無し」のまま） |
| W-3 | B が T1（ワークスペースは既にあり、停止中）で Console を開き、受信箱の画面で既読・引き受け・辞退・完了・手放しをする | B のワークスペースの `state` が `stopped` のまま。起動するのは、B が依頼から**起動**を押したときだけ |
| W-4 | （P1-A 後半）W-2 の B がレシピを取り込む | メモの列に 1 件増え、`workspace` の行は増えない。取り込みは `withMembership` のルートである（メモの送信 `POST /api/memos/flush` は `withResolved` で、それは受信箱の外の操作） |

**Go のテスト**: 受信箱のすべてのルートについて、ワークスペースのレコードが無い membership で呼んでも
`workspace` に行ができないことをハンドラのテストで示す。新しいルートを `withResolved` で登録したら
落ちるように、ルートの一覧から機械的に回す形にする。

## 130.6 取り込むまでエージェントから見えない（決定 1・3）

| ID | 操作 | 合格の条件 |
|---|---|---|
| T-1 | A が B にレシピ付きの依頼と DM を送る。B は取り込まない。B のセッションで `list_memos` を呼ばせる。B のメモを送信（flush）する | `list_memos` の結果に受信箱の本文が無い。flush で送られた本文にも無い |
| T-2 | （P1-A 後半）B が引き受けてから取り込む。もう一度 `list_memos` | 取り込んだ 1 件だけが出る。CP が付けた `origin`（送信者と項目 id）が付いている |
| T-3 | （P1-A 後半）担当者でない C が、同じ依頼のレシピを取り込もうとする。B が取り込みを 2 回押す | C は断られる。B の 2 回目は新しいメモを作らない（(項目, 担当者) ごとに冪等。決定 2） |
| T-4 | （P1-A 後半）取り込んだメモを、自分のメモ 2 件と一緒に送る | 取り込んだメモは単独の 1 通で、`origin` 付きで送られる（決定 3）。自分のメモと連結されない。Console の送信画面で本文を編集した場合も同じ |

## 130.7 CP と Agent の版違い

受信箱そのものは CP と Console（CP が配る）だけで動き、Agent を通らない。版違いが効くのは、①取り込んだ
レシピがメモとして Agent に渡るところ、②依頼から起動するところ、③CP の版上げで新旧の CP が重なる
ところ（`minimumHealthyPercent=100` で約 51 秒）、④CP を戻したとき、の 4 か所である。走っている
ワークスペースの Agent は、ワークスペースを再起動するまで古い版のままなので、①②は普通に起きる。

| ID | 操作 | 合格の条件 |
|---|---|---|
| V-1 | 受信箱のある CP に上げ、B のワークスペースは上げる前から走らせたまま（古い Agent）にする。§130.2〜130.6 の受信箱の操作をする | すべて新しい Agent のときと同じ結果になる |
| V-2 | （P1-A 後半）V-1 の古い Agent のセッションで、取り込んだメモに `list_memos` と `update_memo`（本文だけ変える）をさせる | `list_memos` に取り込んだメモが出る。`update_memo` の後も `origin` が残る（CP は部分更新で、渡されない欄を消さない） |
| V-3 | （P1-A 後半）新旧どちらの Agent からでも、`add_memo` と `update_memo` の引数に `origin` を書かせる | CP は無視するか断る。`origin` はサーバーが付けたもの以外にならない（決定 3。Agent は引数をそのまま CP に渡すので、守れるのは CP だけ） |
| V-4 | 古い Agent のワークスペースで、依頼から起動する | セッションが起動する。依頼のカードに、起動したセッションと作業コピー・ブランチが記録される（CP 側の記録なので Agent の版に依らない）。セッション側の出自バッジが古い Agent で出せないなら、出ないだけでエラーにならない |
| V-5 | CP を版上げする間（新旧が重なる約 51 秒）に、Console から受信箱を開き、引き受けを押す | 古い CP に当たった要求は 404 になり、Console は「受信箱を読み込めない」と出して再試行する（真っ白にならない・赤いエラーが残らない）。新しい CP に当たった引き受けは、その後の状態と矛盾しない |
| V-6 | 新旧が重なる間に古い CP がメンバーを物理削除する（古い CP の削除は受信箱の表を知らない） | 残った受信箱の行は、M-8 の消去処理が孤児として消す |
| V-7 | CP を受信箱の無い版へ戻し、もう一度上げる | 戻した CP は、受信箱の表が増えたデータベースのまま起動し、普通に動く（追加だけの移行）。上げ直すと項目と状態が戻す前のまま見える。受信箱を知らない古い Console のタブを新しい CP に向けたままでも、エラーが出ない |

**移行の版番号**: 並行の P1-B（#1962）も移行を足す。マージの前に、両方言の移行の版番号が develop と
重なっていないことを確かめる（同じ版が 2 つあると、マージ後に全テストが赤くなり、PR どうしの git の
衝突検査では出ない）。

## 130.8 決めておくこと

ADR 0111 の本文から一意に読めない点が 2 つある。P1-A の PR はこれを決めてから条件を当てる。

1. **ブロックされた送信者に何を返すか**（A-6）。黙って成功を返す（ブロックされたことを送信者に知らせない）か、
   断る（送信者は届かないことを知る）か。
2. **取れる受け手が 1 人もいなくなった `open` の依頼**（M-2 で C がいないとき。全員が削除またはブロック）。
   決定 2 の「数えない」を字義どおりに当てると、数える人がいない＝「全員辞退」で `declined` になる。
